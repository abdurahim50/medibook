# Security

## Reporting a vulnerability

Please do not open a public issue. Report vulnerabilities privately through GitHub: **Security → Report a vulnerability** on this repository. Include the affected endpoint, steps to reproduce and the impact you observed.

## Security model

| Area | Control |
| --- | --- |
| Identity | Patient identity is derived only from the session token, never from request data |
| Authorization | Every appointment query is scoped to the signed-in patient; records owned by others return `404` |
| Passwords | argon2id hashing; minimum length 12; plaintext never stored or returned |
| Sessions | 256-bit random tokens; only a SHA-256 digest is stored; 8-hour expiry; revoked on sign-out |
| Sign-in | Identical `401` for unknown email and wrong password, and each performs one argon2 verification; this removes the large timing difference, though response times are not guaranteed identical |
| Sign-in throttling | Failed sign-ins limited per account (5) and per client (20) in a 15-minute window; further attempts return `429` |
| Input validation | Strict typing, length limits and rejection of unknown fields on every request body |
| Data integrity | Foreign keys enforced; `UNIQUE(slot_id)` prevents double booking, including under concurrent requests |
| Database access | Parameterised queries only; the API's database role can read and write rows but not change the schema, `TRUNCATE` or own tables; it signs in with 15-minute RDS IAM tokens and has no password |
| Secrets | No credentials in the repository; `.env` files are git-ignored; the database admin password is generated by RDS and given only to the migration task |
| Audit logging | JSON audit events for sign-in, booking and appointment access, containing identifiers only; cross-patient attempts logged as `denied` |
| Container | Non-root user, read-only root filesystem, capabilities dropped, base image pinned by digest, image scanned in CI |
| Delivery pipeline | Every change to `main` goes through a pull request that must pass tests, SAST, dependency, secret and image scans, policy tests, an authenticated DAST scan and a policy-checked Terraform plan of both stacks |
| HTTP security headers | `nosniff`, `no-store`, restrictive CSP, `X-Frame-Options: DENY`, `Cross-Origin-Resource-Policy: same-origin` and `Referrer-Policy: no-referrer` on every response |
| Infrastructure policy | Every Terraform plan is checked against Conftest policies (network exposure, IAM wildcards, container hardening, encryption, retention, tagging) before apply; the policies are unit-tested in CI |
| Supply chain | Python dependencies installed from a lock file with SHA-256 hashes for every package (pip-tools, `--require-hashes`); images are built and published only by the release workflow on `main`, through GitHub OIDC (no stored AWS keys); each image has a CycloneDX SBOM and a keyless Cosign signature and attestation, verified before deploy |
| Data minimisation | No symptoms, diagnoses, date of birth, insurance or payment data collected |

Each control is mapped to NIST SP 800-53 with its evidence in [docs/controls.md](docs/controls.md).

## Known issues

| ID | Severity | Summary | Status |
| --- | --- | --- | --- |
| MB-001 | High | `GET /appointments/{id}` checked that the caller was signed in but not that they owned the appointment, so a signed-in patient could read another patient's booking by ID (broken object-level authorization). | **Fixed.** Lookup is scoped to the session's patient; other patients' IDs return `404`. Covered by a regression test. |
| MB-002 | Medium | `/auth/signin` accepted unlimited attempts, allowing online password guessing and credential stuffing. | **Fixed.** Failed sign-ins are throttled per account and per client; blocked attempts return `429` and are audited. |
| MB-003 | Medium | No record of sign-in, booking or appointment access, so probing and misuse went unnoticed. | **Fixed.** Structured audit log with request IDs; cross-patient attempts are logged as `denied`. |
| MB-004 | Medium | In AWS, Uvicorn trusted `X-Forwarded-For` from any source (`--forwarded-allow-ips=*`) and took the leftmost address, which the client writes. A client could choose the address recorded in the audit log and spread failed sign-ins across fake addresses to avoid the per-client throttle. Found in external review, 2026-10-09. | **Fixed.** Only the load balancer's subnets are trusted, so the address the ALB appended is used. Regression tests show the forged address ignored; verified in AWS on 2026-10-12. |
| MB-005 | Low | Slots whose time had passed were listed and could be booked. Found in external review. | **Fixed.** Past slots are not listed; booking one returns `409`. Tests added. |
| MB-006 | Medium | Slow statements (over 1 s) were logged with their bind parameters, which can include emails and password hashes; PostgreSQL logs them in full by default. Found in external review. | **Fixed.** `log_parameter_max_length` and `log_parameter_max_length_on_error` set to `0` in the parameter group. Verified in AWS on 2026-10-12: a slow statement with a synthetic email was logged without its parameters. |
| MB-007 | Low | The destructive-SQL alarm matched `DROP TABLE` and `drop table` only; CloudWatch patterns are case-sensitive, so `DrOp TaBlE` was missed. Detection only: the API's role cannot drop tables. Found in external review. | **Fixed.** An event trigger raises the same `DESTRUCTIVE_SQL` warning for every dropped table, however it is spelled, and refused attempts match on the server's own error text. Tests cover case and whitespace variants. Verified in AWS on 2026-10-12: `DrOp TaBlE` alarmed in 1 min 47 s. |
| MB-008 | Medium | Sign-in skipped password verification for unknown emails, so an unknown email answered measurably faster than a wrong password despite the identical `401`. Sign-up answers `409 Email already registered`, which confirms an account exists. Found in external review, 2026-10-09. | **Sign-in fixed:** unknown emails are verified against a dummy argon2 hash; test added. **Sign-up accepted for now:** the `409` stays, because without an email service there is no other way to tell a returning patient their account exists; sign-up is now rate limited per IP in AWS WAF with sign-in (verified 2026-10-12: blocked from request 161). Planned: confirm-by-email sign-up that answers the same way for new and existing emails. |
| MB-009 | Low | Validation errors (`422`) echoed the submitted value, so a password rejected for its length came back in the response body, where proxies, debugging tools or client logs could keep it. Found in external review, 2026-10-12. | **Fixed.** Validation errors name the field and the rule only; tests cover short and long passwords, a missing field, a bad email and an unknown field. Verified in AWS on 2026-10-13. |
| MB-010 | Low | The sign-in throttle removed a key's expired failures only when that same key was checked again, so one-off emails and addresses stayed in memory indefinitely; enough of them could exhaust a container's memory. Found in external review, 2026-10-12. | **Fixed.** Expired keys are removed on every recorded failure, and each limiter holds at most 100,000 keys; at the cap the longest-idle key is dropped and a warning logged. Tests added. |

## Limitations

- The dev database is a single-AZ RDS instance deleted with the environment; production needs Multi-AZ and deletion protection.
- Migrations run from GitHub Actions through a role that can start only the migration task, in a protected environment that needs an approval and allows `main` only; only the migration task's execution role can read the admin credentials (F-8). Two limits remain: an AWS administrator can still run anything (a separate account or an organization policy is the production control), and ECS offers no IAM condition on command overrides, so the migration role's safety rests on the reviewed workflow being its only user. Verified in AWS on 2026-10-14. The approval rule itself is a GitHub environment setting, not code; it was missing for the first two runs (F-17).
- Sign-in throttling is held in memory per container; the shared control across containers is the edge rate limit. A throttle can be triggered on another patient's account for up to 15 minutes.
- Audit events go to CloudWatch Logs (7-day retention in dev). Alarms fire on 5 or more denied requests in 5 minutes and on `DROP` or `TRUNCATE` in the database log, and when the API cannot reach the database (each task checks once a minute, with or without traffic, F-12). Alarms notify an SNS email subscription that must be confirmed after each new deployment; `scripts/check-alerting.sh` fails until it is (F-13). Known alerting gaps: a false database-unreachable alarm during each fresh deployment until the migration runs (F-15), and a total API outage alarms only after about 9 minutes (F-16).
- Unfixed operating-system CVEs in the base image are triaged in [docs/vulnerability-exceptions.md](docs/vulnerability-exceptions.md).
- Email format is checked with a pattern, not verified by confirmation email.
